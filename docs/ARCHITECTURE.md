# NFT Tracker — анализ реализуемости и архитектура

## 1. Что реально можно получить от Telegram

| Функция | Bot API (токен бота) | MTProto (пользовательский аккаунт) |
|---|---|---|
| Типы `UniqueGift`, `UniqueGiftModel/Symbol/Backdrop` | Да, но только как часть подарков, которые *видит бот* (`getUserGifts`, `getChatGifts`, `getBusinessAccountGifts`, сообщения с `UniqueGiftInfo`) | Да |
| Каталог подарков (`getAvailableGifts`) | Да, но это каталог **для отправки**, а не рынок | `payments.getStarGifts` |
| **Лоты на маркетплейсе перепродажи** (цена, владелец, атрибуты) | **Нет метода** | `payments.getResaleStarGifts` (gift_id, sort_by_price / sort_by_num, offset, limit, фильтр по атрибутам) |
| Push о появлении нового лота | Нет | Нет — только поллинг |
| Ссылка на подарок | `https://t.me/nft/<slug>` (slug = `PlushPepe-1234`) | то же |
| Владелец | Только для подарков, которыми бот управляет | `StarGiftUnique.owner_id` / `owner_name` для лотов; публичная ссылка возможна лишь при наличии `@username` |

Выводы:

1. **Bot API не даёт доступа к рынку** — это ограничение платформы. Бот-аккаунт (токен) нужен только для общения с пользователями.
2. Единственный официальный источник лотов — **MTProto API** (`payments.getResaleStarGifts`). Для него нужен `api_id`/`api_hash` с <https://my.telegram.org> и **один служебный пользовательский аккаунт оператора** (не аккаунты пользователей бота!). Сессия оператора хранится как секрет в `.env`.
3. Мгновенного обнаружения нет: бот **опрашивает** рынок. Задержка = длительность цикла опроса (по умолчанию ~1–3 минуты в зависимости от числа коллекций и `SOURCE_REQUEST_DELAY`).
4. Автоматизация пользовательского аккаунта подпадает под Telegram API Terms; поэтому: низкая частота, пауза между запросами, обработка `FloodWait`, отдельный аккаунт.
5. Сторонние маркетплейсы (Portals, Tonnel, MRKT и т. п.) имеют **недокументированные/неофициальные** API — в MVP они не используются. Для них оставлен интерфейс `GiftSource`.
6. «Покупка/сделка» — только по ссылке на подарок в самом Telegram. Бот сделок не проводит и не утверждает, что они состоялись.

### Что работает в этом MVP, а что требует доп. источника

| Функция | Статус |
|---|---|
| Весь интерфейс бота, фильтры, уведомления, дедупликация, статистика | работает (проверено тестами) |
| Источник `mock` (демо-данные для разработки) | работает без внешних зависимостей |
| Источник `telethon` (реальный рынок) | реализован по документированному TL-API; **требует** `TG_API_ID`, `TG_API_HASH`, `TG_SESSION_STRING` (см. README). В CI/песочнице без аккаунта не запускался — парсер ответа покрыт тестами на реальных TL-типах Telethon |
| Владелец лота | показывается `@username` + ссылка, если он публичен; иначе имя (если отдано API) или «скрыт» |
| Мгновенные уведомления | **нет** (поллинг) |
| Охват рынка | первая страница лотов на коллекцию, отсортированная по дате (новые первыми) |

## 2. Выбор подхода

Рассмотрено три варианта источника:

* **A. MTProto через Telethon (выбран).** Официальный протокол, полные данные (атрибуты, цена, владелец), стабильные TL-определения. Минус: нужен служебный аккаунт.
* B. Сторонние маркетплейсы по неофициальным API. Нестабильно, возможны нарушения их правил.
* C. Только Bot API. Рынка нет — функция невозможна.

Источник абстрагирован интерфейсом `GiftSource`, так что B можно добавить позже, не трогая остальной код.

## 3. Архитектура

```
                ┌────────────────────────── процесс "bot" ──────────────────────────┐
 Telegram Bot   │  aiogram Dispatcher (FSM в Redis/Memory)                          │
 API  ◄────────►│   ├─ middlewares: DbSession (+upsert user), Throttle              │
 пользователи   │   └─ handlers: start / search / filters / notifications / stats / help
                │                                                                   │
                │  Monitor (asyncio task)                                           │
                │   1. берёт активные фильтры → решает, какие коллекции опрашивать  │
                │   2. GiftSource.list_collections / fetch_listings (rate-limited)  │
                │   3. сохраняет лоты (listings), первый проход коллекции = baseline│
                │   4. матчит новые лоты с фильтрами → Notifier (дедуп в БД)        │
                └───────────────┬───────────────────────────────┬───────────────────┘
                                │                               │
                   PostgreSQL (users, filters,        GiftSource: TelethonGiftSource
                   listings, notifications,                      | MockGiftSource
                   poll_state)                         Redis: FSM-хранилище (опционально)
```

Ключевые решения:

* **Дедупликация**: таблица `notifications` с `UNIQUE(user_id, listing_key)`; `listing_key = slug|price|currency`. Вставка `INSERT … ON CONFLICT DO NOTHING RETURNING id` атомарна — уведомление отправляется только если строка вставлена. Изменение цены = новое предложение = новое уведомление. Один лот, подошедший под несколько фильтров пользователя, даёт одно уведомление.
* **Baseline**: при первом опросе коллекции (и после простоя фильтров) лоты только запоминаются, без рассылки — иначе пользователи получили бы сотни «новых» лотов.
* **Семантика доставки** — «не более одного раза»: строка уведомления создаётся до отправки; при сбое доставки повтора нет (логируется).
* **Лимиты**: глобальный лимитер исходящих сообщений (`NOTIFY_RATE_PER_SECOND`, по умолчанию 20/с при лимите Telegram ~30/с), обработка `TelegramRetryAfter`, пауза между MTProto-запросами и `FloodWait`, троттлинг пользовательских апдейтов.
* **Блокировка бота пользователем** (`TelegramForbiddenError`) → `users.is_blocked = true`, рассылка ему прекращается до следующего `/start`.
* **Приватность**: хранятся Telegram ID, username, имя пользователей бота и их фильтры. Паролей/кодов входа нет. Сессия оператора — только в переменных окружения.
* **Мини-приложение**: тот же процесс поднимает aiohttp-сервер (статика + `/api/*`). Каждый запрос подписан `initData` (HMAC от токена бота, проверка срока), пользователь создаётся атомарным `INSERT … ON CONFLICT` (приложение шлёт несколько запросов параллельно). Telegram требует HTTPS, поэтому перед сервером стоит Caddy или туннель.
* **Масштабирование** (за рамками MVP): матчинг в Python по всем активным фильтрам за цикл; миграции — через `create_all` (для продакшена подключить Alembic); несколько воркеров опроса требуют advisory-lock.

```
├── tests/
├── Dockerfile  docker-compose.yml  requirements*.txt  .env.example  README.md
```
